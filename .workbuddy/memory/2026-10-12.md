## 排查「托盘未读数字不清理」——确认是 WorkBuddy 造成的

用户报托盘数字清不掉，怀疑 WorkBuddy。用真实日志 + 运行态 + 一次可控复现证实。

### 事实

- 托盘数字 = `update_tray_attention()`，`ActivityState.by_provider` 里
  `!attention_seen && 24h 内 && state ∈ {failed,needs_input,needs_approval,blocked}` 的行数。
- 抓 `~/Library/Application Support/com.dushaobin.lingxi-desktop/logs/task-events.log`
  （脱敏 JSONL：`dir=in` 带 `payload`，字符串值只记 `str(len)`）。
  当天 workbuddy 时间线呈现固定节律：**Stop(completed) → +60.0s → echo needs_input**，
  13:51:04 / 14:15:52 / 14:27:29 / 14:50:08 / 14:54:24 / 16:49:58 全部命中。
  来源 summary 是 `WorkBuddy 等待用户（hook 提示）`，原文 `CodeBuddy is waiting for your input`。
- 当前 `/activity` 55 行：托盘 7 个未读里 **5 个是 workbuddy**；24h 之外残留的 10 行里 **9 个是 workbuddy**。
- 放大器：**每个 WorkBuddy 会话一个 key**（hook 带 36 字符 session UUID → `workbuddy#<uuid>`），
  所以未读按会话累积，不会互相覆盖。
- 另一类非 echo 的 needs_input 来自 Stop 的 `closing_question`（回复末尾真提问，
  如「要不要把这次重推也写进报告」）——行为正确，但同样挂着。

### 运行版本 ≠ 源码版本（关键坑）

`/Applications/灵犀.app/Contents/MacOS/lingxi` 二进制时间 **2026-10-08 10:42**，
早于 dd74ded（10-09「clear tray unread reminders」，引入 `attention_seen` /
`acknowledge_activity` / `/activity` 的 `attention` 字段）。
判据：`GET /activity` 返回行里**没有 `attention`、`attention_seen`、`key` 字段**。
所以当前这个进程**没有"已读"机制**：打开主界面也清不掉，只有 24h TTL 或新事件覆盖才消失。

### 复现方法（可复用，低侵入）

用独立 id 探针，不碰真实会话行，事后发 completed 覆盖清理：

    POST /task-event {"state":"completed","origin":"hook","kind":"chat",
      "provider":"lingxi-probe","agent":"lingxi-probe","session":"tray-probe-1",...}
    再 POST 同 session 的 {"state":"needs_input","echo":true}

结果：探针行 completed → needs_input，`/activity` 推断托盘数字 **7 → 8**，再发 completed 回到 7。

### 更正一个判据（重要）

那是 tauri command `get_agents` 给主界面的。所以"没有 attention 字段"**不是**版本判据。
可靠判据：在二进制里搜符号——新包含 `acknowledge_activity`，旧（10-08）不包含。
（"运行的是 dd74ded 之前的旧版本"这个结论本身没错，只是原来的证据用错了。）
