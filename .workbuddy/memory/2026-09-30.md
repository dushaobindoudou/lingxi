原来是 `/Users/liepin/.workbuddy/binaries/node/versions/22.22.2-3/bin/node`。

### 两个踩坑（都写进注释了）

1. **`node:sqlite` 的 ExperimentalWarning 脚本内部压不掉**。node 22 实测：装了
   `process.on('warning')` 照样往 stderr 打印。所以 **python3 先跑、node:sqlite 兜底**
   （反直觉但正确），hook 命令仍带 `--no-warnings` 是给兜底路径用的。
2. **`execFileSync` 默认继承父进程 stderr** → python traceback 会漏进宿主 hook 输出。
   必须显式 `stdio: ['ignore','pipe','pipe']`。
3. `install.sh` 里 `[ -n "$VAR" ] && log ...` 在 `set -euo pipefail` 下，VAR 为空会让
   安装器死在最后一步。改成 `if`。

## "WorkBuddy 弹出问题，没有 hook 吗" → 补装 Notification / PermissionRequest

诊断：hooks **在跑**（事件流里有 workbuddy 的 running，守卫状态文件里另一个 session 已记到
tier 0.6）。问题是**只装了两条生命周期事件，弹窗根本不在覆盖范围**。

查证（官方文档 workbuddy.ai/docs/cli/hooks + 一个第三方包的实测 census，APP 5.5.4）：
WorkBuddy 的引擎是 Claude Code 形状的 hook manager，支持
`PreToolUse / PostToolUse / Notification / UserPromptSubmit / Stop / SubagentStop /
PreCompact / SessionStart / SessionEnd`。census 实测 SessionStart 会触发 2 次
⇒ **之前"WorkBuddy 没有 SessionStart / Notification"那条结论是错的**，已订正 plugin/README.md。

应用侧早已支持（lib.rs:1172 Notification、1227 PermissionRequest，
1423 起的事件白名单里两个都有），emit 适配器的 fromClaude 也早有映射。缺的只是**装**。

改：install.sh 的 EMIT_EVENTS = 4 个，GUARD_EVENTS 仍是 2 个（守卫读整会话用量，跟弹窗无关）。
⚠️ 实现上必须**一个循环内**清空+写入——`owned()` 把 emit 和守卫都认作 lingxi 的，
分两个循环的话第二个循环会把第一个刚写的 group 删掉。
plugin/hooks/hooks.json 同步 4 个事件（守卫只在 2 个上）；测试改断言 4 事件 +
Notification/PermissionRequest 各只要 1 个 group。

实测：喂一个 Notification 载荷 → 事件流出现 `needs_approval | workbuddy | 想用 Bash，等你批一下`。
所以下次 WorkBuddy 真的弹权限/提问时猫会反应。

**刻意不装 PreToolUse/PostToolUse**：每次工具调用都触发，会把猫变成通知轰炸。
（`PreCompact` 也没装：emit 对它返回 null，装了不会有反应。）
