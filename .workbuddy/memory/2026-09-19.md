### 最严重的一条：#7 `/intent` 无校验 → 猫消失


1. `main.ts:340` 只判 `if (targetPoint)`，空对象是 truthy，直接透传；
2. `life-engine:727-734` 的 `clamp(targetPoint.x, minX(), maxX())` 是**虚假防御** ——
   `clamp` 是 `Math.min(Math.max(v,min),max)`，`Math.max(undefined,24)` = NaN，clamp 透传 NaN；
3. `heading` 与 `position` 同时 NaN，`moveToward` 里 `atan2(dest.y - NaN, ...)` 持续产出 NaN
   → **NaN 自我维持**。

**恢复不可靠（实测）**：`{"resetPosition":true}` 返回 ok+applied，`main.ts:350` 也确实监听了
`reset-position` 并调用 `engine.resetPosition()`，但**之后连续采样 24 秒位置仍非法**。
`resetPosition()`（index.mjs:790-800）重置了引擎侧变量，**没重置 `heading`，也没触及渲染层平滑状态**。
约 10 分钟后猫**自行恢复**（位置回到左边缘 x≈32），但**恢复触发点无法确定** ——

（既定行为）。换用时长 4.5s 的 `wb-suspend` 后 `action` 字段全程如实反映。
→ **教训**：单次采样看到的 `action` 可能是**上一个**自主动作，不能据此判定本次失败。
这与 skill 里"动作有延迟别以为没生效就重发"是同一条，但这次区别更微妙
—— 不是"还没开始"，而是"看到了别人的动作"。

### 新结论：#6 是 #3.1 能否被发现的前提

`expression` 转发对**内外置一律返回相同的 200 (forwarded)**，而观测面上没有任何字段
能区分"换成功了"和"拼错了"。40 个表情里打错一个，驱动方**完全瞎飞**。
→ 补齐 #6（`/perception` 暴露 `expression`）不是可观测性的锦上添花，
而是假成功能否被发现的**必要条件**。这条已写进 ISSUES 的实测补记。

### #14 的静态补充证据（本轮）

桥暴露的路由全集：`/capabilities /control /intent /memory /perception /reminders /status /task-event`
—— **无任何 assets 相关端点**。实测 `POST /control {"reloadAssets":true}` → 400
`empty command: expected at least one of camera/skin/scale/visible/action/expression/perform/toy/say/resetPosition`
（即该字段根本没被识别）；`POST /assets/reload` → 404。
`reload_custom_assets` / `get_custom_assets` / `get_asset_errors` 都只是 Tauri command（lib.rs:1529/1625/1631），
agent 不可达。**#14 确认，且修法已明确。**

## 第五轮：用户反馈"重载了也没看到"（09:20）—— #13 深挖到根

用户怀疑资源写错了位置（"应该放到安装的 application 下，而不是写到源代码下"）。
**位置是对的，但顺着这条线挖出了一个比原 #13 严重得多的事实。**

### 先排除位置嫌疑（全部实测）

- 运行进程 = `lsof -p 46074 -a -d txt` → **`/Applications/灵犀.app/Contents/MacOS/lingxi`**，就是安装版。
- 它读的目录：bundle id `com.dushaobin.lingxi-desktop` → `~/Library/Application Support/com.dushaobin.lingxi-desktop/`。
  **安装版与源码构建版共用同一 bundle id，因此共用同一 Application Support 目录。**
  把资源写进 `.app` 包内反而会被下次构建覆盖 —— 现在的位置是唯一正确的。
- `git status --short` 只有 `ISSUES-2026-09-19.md` —— **源码树零污染**，我从没往源码树写过资源。
- 用户其实在 09:14 重新构建过 `dist`、09:16 重装并重启了 app（时间戳），也没能解决。

### 真因：外观页不读自定义资源

`management.ts:16` `import skinCatalogue from './data/skins.json'` → 编译期打包进 `dist/`。
`management.ts:202` 卡片只从 `SKINS`（该静态目录）生成。该文件只有 **9 条内置，无自定义项**；
实测 `grep -r workbuddy-mint apps/lingxi/dist/` 与 `/Applications/灵犀.app/` **都搜不到**。
→ **点多少次重载都不会出现卡片。**

### 四道门（任何一道都足以挡死自定义皮肤）

| # | 门 | 位置 | 行为 |
|---|---|---|---|
| 1 | 外观页卡片列表 | `management.ts:202` 静态 `data/skins.json` | 不生成卡片，用户看不见 |
| 2 | UI 点击 → `set_skin` | `lib.rs:399` `apply_skin` | **静默回落 `DEFAULT_SKIN`**，无提示 |
| 3 | `/control`（agent） | `lib.rs:865` | 400 |
| 4 | 启动恢复 | `lib.rs:266` | 回落 `default_skin()` —— **活不过重启** |

净结果：**`workbuddy-mint` 是一份「加载了但谁也够不到」的资源** ——
用户 ❌、agent ❌、无可见入口 ❌。而重载**确实生效了**（`wb-suspend` 实测能播、
capabilities 已更新），所以用户看到的唯一反馈就是那行小字「已重新加载。」

### 副产物：一个 UI 承诺与现实的落差

`management.html:225` 写「动作、表情、主题都是可编辑的 JSON…改完点「重新加载」即可生效」——
对动作/表情（agent 侧）成立，对**主题**完全不成立。这句话让用户以为改完就能用。

### 顺带修正了自己写错的 skill

`interface.md` 第七节原来写「自定义皮肤要去请用户在「外观」页里选」—— **这是错的**，
外观页根本不显示它。已改成：明确告诉用户"你和我在当前版本都用不了自定义皮肤"，
并加了一条硬约束：**不要为了让它生效去改源码或重新构建**（那是修复动作，不是驱动动作）。
`library.md` 的 skins.json 一节也补了同样的警告。

### 方法论收获（可复用）

判断"应用到底读哪个目录"的可靠姿势：
`lsof -nP -i :端口` 拿 PID → `lsof -p <PID> -a -d txt` 拿可执行路径 → 对照 `Info.plist` 的 bundle id。
比读代码猜路径快得多，而且能顺带确认"跑的是安装版还是开发版"。
（注：本轮 `ps aux` 在此 sandbox 下读不到进程，`lsof` 可以。）
