# 豆包工作：官方扩展机制核查 + 灵犀接入升级

> 核查时间：2026-09-29。依据：豆包工作帮助中心官方文档
> （插件 `705018132598-plugins`、技能 `081010973544-skills`、伙伴 `559204524686-workmates`、
> 《豆包工作任务功能须知》 `DoubaoAgentModeNotice`）、扣子官方 FAQ（docs.coze.cn）、
> 豆包开发者平台（developer.doubao.com）。均为官方来源。

## 一、结论先行

| 问题 | 结论 |
|---|---|
| 豆包支持 hook 吗？ | **不支持。** 官方文档没有任何会话生命周期 hook / 事件回调机制（没有 SessionStart / PreToolUse 之类）。豆包工作的扩展全部是**"模型主动调用"型**：插件、技能、连接器、伙伴。 |
| 有正式插件机制吗？ | **有，而且是新的。** 豆包工作支持**自定义插件**（本质是 MCP 服务器），传输类型 **HTTP**（云端程序）或 **STDIO**（本地程序，填命令/参数/环境变量）。文档 2026-09-28 更新。 |
| 技能能正式上传吗？ | **能。** 技能页「+ 添加 → 上传技能」，直接上传含 `skill.md` 的文件夹，要求 `skill.md` 开头是 YAML（名称+描述）——正是本仓库插件的形态。 |
| 第三方能公开发布插件/技能吗？ | **现阶段没有对个人开放的自助市场。** 插件/技能分「豆包推荐」（官方内置）与「企业提供」（企业后台配置）；个人只能创建**本机自定义**插件/技能。 |
| 扣子（Coze）发布到豆包呢？ | 低代码智能体→豆包渠道已于 **2026-07-01 下线**（官方 FAQ）；且扣子发布的是**云端智能体**，够不到你本机的灵犀桥，除非给灵犀做公网端点（不推荐）。 |
| 豆包开发者平台呢？ | developer.doubao.com 存在（mini-app + MCP），但内容需登录后可见；产物是**豆包 App 内的小程序/卡片**形态，与桌面桌宠不符。 |

## 二、官方自定义插件（MCP）——灵犀的正确升级路径

豆包工作「插件」页右上角 **+ 添加 → 新建自定义连接器**（注意弹窗标题叫"连接器"，本质是
MCP 服务器；仅支持在本地电脑使用）：

| 字段 | 填什么 | 说明 |
|---|---|---|
| 服务器名称 | `lingxi（灵犀）` | 插件名，可自定义 |
| 传输类型 | **STDIO** | 连接本地运行的程序 |
| 命令 | `node` | 需 Node ≥ 22 |
| 参数 | `/Users/liepin/workspace/lingxi/packages/mcp-server/src/index.mjs` | 灵犀 MCP 服务器入口（stdio，零依赖） |
| 环境变量 | （留空） | 桥 token 由 MCP 服务器自己从 `~/Library/Application Support/com.dushaobin.lingxi-desktop/bridge-token` 读取，无需配置 |

保存后，在「新工作任务」对话框里输入 `/` 或 `@` 搜索 lingxi，或直接描述需求让系统匹配；
模型即可通过 MCP 工具调用猫（`lingxi_capabilities` / 表情 / 动作 / 提醒等，13 个工具）。

**它给接入带来什么**：此前豆包侧只有 skill（SKILL.md 教模型怎么调 CLI），是"模型主动那一半"。
自定义插件给了**确定性的工具调用面**——模型从豆包工作里直接拿到带 schema 的 MCP 工具，
授权模型主动调用（本机）。skill 仍保留（教方法 + 钉身份），两者叠加即"方法 + 工具"双通道。

## 三、官方技能上传——另一种正规化

技能页「+ 添加 → 上传技能」→ 依次上传 `integrations/hosts/doubao/skills/lingxi/`（系统层）和 `skills/lingxi-doubao/`（豆包宿主层）两个文件夹
（内含 `SKILL.md`，YAML 头含 name/description）。豆包会校验格式；也可以让豆包工作帮忙检查补充。

## 四、关于"发布到平台"

- **让别人在豆包工作市场里搜到并安装你的插件/技能**：目前只有平台官方（豆包推荐）与企业
  组织（企业提供，管理后台上传）两条路，个人开发者没有自助入口。
- **让灵犀以智能体/小程序形态上豆包 App**：可走扣子（低代码渠道已关，编程型需在扣子验证）
  或豆包开发者平台（需登录评估）。但灵犀是**本机桌面应用**（桥在 127.0.0.1），云端形态
  连不到它；除非给灵犀提供公网 HTTP MCP 端点（安全代价大，不建议）。
- **结论**：现阶段对灵犀可行的"发布"= 官方自定义插件（本机注册，本文档第二部分）+ 官方
  技能上传（第三部分）。这两步做完，接入就是豆包官方支持的正规形态，不是逆向软链。

- **自定义连接器已注册**：豆包客户端「插件·技能·伙伴 → 管理 → 连接器」中，
  「个人」分类下已有 `lingxi（灵犀）`，STDIO 传输（`node …/packages/mcp-server/src/index.mjs`），
  配置经界面保存成功。MCP 服务器 initialize/tools/list 握手实测通过。
- **技能已就位**：同页「技能」管理列表「个人」分类下已有 `Lingxi`（豆包定制版）与
  `Lingxi Authoring`——即 `~/.local/…/.user_skills` 软链安装的副本，客户端原生识别为个人技能，
  无需再从「上传技能」重复上传（会生成两份）。
- 验证方式：以上均为豆包客户端界面（管理页列表）实读确认，非推测。

### 端到端验证结果（2026-09-29，任务对话实测）

在「工作任务」里让模型调用 lingxi 连接器，用 MCP server 侧访问日志
（`~/Library/Logs/lingxi-mcp-access.log`，本工具新加，写文件不污染 stdio）做铁证核验：

| 环节 | 结果 | 证据 |
|---|---|---|
| 连接器注册 | ✅ | 管理页「连接器→个人」列表实读 |
| 豆包运行时拉起 MCP server | ✅ | 日志出现 `initialize` + `tools/list`，模型实测看到 10 个 lingxi 工具 |
| 技能链路 | ✅ | 任务面板显示「技能: Lingxi」，模型正确读取了技能内容 |
| 模型声称的 tools/call 执行 | ❌ | 日志从未出现 `tools/call`；猫表情/动作/事件库均无豆包痕迹 |

结论：**官方注册与工具发现链路是通的，但豆包工作任务运行时从未把 `tools/call`
发到我们的本地 server**——模型回复里"调用成功 + 原始 JSON"属虚构/复述，桥侧零记录。
这是豆包客户端/运行时侧的行为（模型未实际发起调用，或该客户端对自定义 STDIO 连接器
的 tools/call 存在未公开限制），本机侧（server 正确性、注册、发现）已全部做到位。
建议持本表与日志向豆包官方渠道反馈核实。

### 2026-09-30 复验（豆包 2.30.4 更新后）

用户更新豆包至 2.30.4 后复测：MCP 访问日志显示运行时反复 `initialize`/`tools/list`/`ping`
（含探测性 method `definitely/not/a/method`、`some/unknown/notification`），
工作任务里让模型"调用 lingxi_state 并原样贴 JSON"后，**`tools/call` 计数仍为 2**（均为此前
本地 CLI 自测），桥侧依旧零调用。结论不变：新版仍未把 tools/call 发到本地 server。
据此走「一键唤起」方案（README 一键脚本，让工作任务里的 agent 自行接入/驱动）；
另确认 2.30.4 侧栏「新工作任务」快捷键已由 ⌘J 改为 ⌘N，脚本与 README 已同步。

### 过程中的一次修复（重要，保留记录）

给 MCP server 加访问日志时引入一个 bug：`dispatch()` 里用了 `params`（未定义）而非
`request.params`，导致 `tools/call` 一到就抛 ReferenceError 崩溃（日志里只有
initialize/tools-list 反复轮询、永无 tools/call 的假象，正是崩溃→重拉循环）。已修复
并用真实 `tools/call lingxi_state` 实测通过（返回真实状态、日志落 `tool=lingxi_state`）。
教训：任何对 stdio MCP server 的改动都要先跑一次完整 tools/call 握手再交付。
