# 决策 002：要不要引入物理引擎 / 游戏框架

**状态**：已决定，2026-09-19
**问题**：既然用了 Three.js，是不是应该接一个游戏类的库，让体系更合理？玩具需要物理特征，
Three.js 支持吗？

## 先回答事实部分

**Three.js 本身没有物理。** 它是渲染器——场景图、材质、相机、光照。碰撞、刚体、约束、
软体都不在它的范围内，需要另外接。

主流选项：

| 方案 | 体积 | 性质 |
|---|---|---|
| **Rapier**（`@dimforge/rapier3d-compat`） | ~1MB WASM | 完整刚体 + 关节 + 碰撞，业界主力 |
| **cannon-es** | ~200KB 纯 JS | 轻量刚体，无软体 |
| **自己写** | ~100 行 | 只解决手上这两个问题 |

## 决策

**不引入通用物理引擎。** 分两块处理：

- **毛线球的运动留在生命引擎里，保持解析式。**
- **逗猫棒的软性尾端用 Verlet 绳**（`apps/lingxi/src/rig/rope.ts`）。

## 为什么

这个应用里想要"物理"的只有两样东西，而它们要的东西完全不同。

**毛线球是玩法，不是画面。** 猫会去追它，它的行为有单元测试，必须是确定性的，而且必须活在
`packages/life-engine` 里——那里没有渲染器、没有 DOM、没有浏览器。把它交给物理引擎意味着：

- 猫的 AI 依赖一个 WASM blob，在 Node 里跑不了测试；
- 生命引擎不再是纯状态机，架构里最干净的那条边界被破坏；
- 为了两个物体启动一个物理世界。

它需要的物理其实只有"滚动 + 摩擦衰减 + 边界反弹"，三行闭式解，而且已经测过了。

**逗猫棒的尾端是画面，不是玩法。** 它不影响猫的决策（猫追的是棒头的位置），它要的是**动量 +
约束**：尾端滞后于手、停手后过冲、之后继续摆动。这正是 Verlet 绳几十年来在游戏里做绳子、
尾巴、布条的原因——四十行，没有依赖，可以在 Node 里测（`packages/life-engine/test/rope.test.mjs`
有 5 个测试覆盖滞后、动量、不拉伸、被打飞、以及长帧不炸）。

还有一条现实约束：**桌宠必须秒开、待机接近零 CPU**。为两个物体常驻一个物理世界不符合这个
前提。

## 什么时候该改主意

如果玩具之间开始**互相碰撞**（球撞到棒、两个球撞在一起、球从桌面边缘掉下去），或者出现需要
真实堆叠/摩擦的场景，那就是 Rapier 的活，自己写会开始出 bug。届时的做法是：把 Rapier 放在
渲染进程里只负责**画面物理**，生命引擎里的玩法物理保持独立——不要让猫的 AI 依赖它。

## 关于"游戏框架"

评估过 Yuka（转向 AI）、Theatre.js（动画编排）这类。结论是**现有架构已经是合理的**：

```
纯行为状态机（可测试，无依赖）→ 渲染器（Three.js）→ 宿主（Tauri）
```

这正是游戏框架会推荐的分层，只是我们自己实现了需要的那一小部分。引入框架会是一次重写，
换来的是我们用不上的功能和一层新的抽象。这个项目的复杂度在**动画质量**（步态、IK、运镜）上，
不在框架缺失上。
