# 决策 003：多个 Agent 同时驱动一只猫

**状态**：已决定，2026-09-19
**问题**：多个 agent 同时驱动会不会互相干扰？来源怎么体现？接入方要满足什么要求？
本机服务需要鉴权吗？

---

## 先把问题说准

"互相干扰"不是一个问题，是三个，它们的解法完全不同：

| 冲突 | 现象 | 性质 |
|---|---|---|
| **表现层抢镜** | A 让猫开心，B 同一秒让猫不爽，猫抽搐 | 时序冲突 |
| **用户设置被抢** | A 换成薄荷皮肤，B 换回奶油色，用户没同意过任何一次 | **越权**，不是冲突 |
| **归属不明** | 猫做了个动作，用户不知道是哪个 agent 干的 | 可观测性 |

第二条最容易被当成第一条来解。它不是并发问题——皮肤、视角、大小、显示与否是**用户的偏好**，
agent 改它本身就是越界的，加锁只会让两个 agent 有序地越界。

---

## 决策一：优先级来自**事件语义**，不来自 agent 身份

这是整个设计的核心，也是最容易做错的地方。

直觉的做法是给 agent 排序——"Claude 比 Codex 重要"。这是错的。用户需要看到的是**哪件事要紧**，
不是哪个工具要紧。构建失败比空闲卖萌重要，**不管是谁报的**。

所以每次表现请求带一个 `priority`，四档，由**事件本身**决定：

| 档 | 值 | 什么时候用 | 例子 |
|---|---|---|---|
| `alert` | 3 | 需要用户**现在**看一眼 | 构建失败、等待输入、危险操作待确认 |
| `report` | 2 | 一件事有结果了 | 测试通过、部署完成 |
| `status` | 1 | 状态变了，不急 | 开始跑了、进度 60% |
| `ambient` | 0 | 纯氛围 | 摸鱼、打哈欠、蹭一下 |

规则：

- **高优先级立刻打断**低优先级，不排队。失败不该等卖萌演完。
- **值得等的排队，不值得等的丢弃**。这一条最初做成了"一律丢弃"，那对氛围是对的，
  对用户真正需要看到的东西是错的：一次构建失败撞上猫正在打呼噜，晚两秒也该播。
  所以 `report` / `alert` 进队列，`status` / `ambient` 直接拒绝。
- **排队的东西都有过期时间**（默认 8 秒，`expiresInMs` 可改）。一个反应是对某个**瞬间**
  的陈述，过了那个瞬间再播不是"迟到"，是"错了"——用户已经在做别的事，猫却在讲历史。
  过期的直接丢掉不播。
- 队列有上限（16），满了先挤掉**优先级最低**的，所以再多的氛围也挤不掉一条 alert。

## 决策二：用户设置 agent 只能读，不能悄悄改

`skin` / `camera` / `scale` / `visible` 是用户的。agent 仍然可以设（不破坏现有接入），
但响应里会明确标注这是用户设置，并且**记进事件日志带上是谁改的**。

agent 想要视觉身份，**用自己的 logo，不要改皮肤**——这正是决策三。

## 决策三：来源用 agent 自己生成的 logo，画在气泡上

agent 注册时提交一个**自己生成的 SVG**。它替猫说话时，logo 出现在气泡角上，**随气泡一起消失**。

**为什么让 agent 自己画，而不是我们提供素材或让用户上传**：写 SVG 正是模型的本行。
它自己生成，就没有素材库、没有上传界面、没有多分辨率，用户什么都不用准备。

**为什么画在气泡上，而不是钉在猫身边**：钉在身上的标记是一个 HUD——它和宠物本身抢注意力，
而且**没有自然的消失时机**（只能拍脑袋定一个超时）。气泡本来就有出现的理由和消失的理由，
把归属挂在它上面，归属就自动只在"有东西需要归属"的时候存在。

**安全**：SVG 放进 `<img>` 渲染，不内联进 DOM。`<img>` 里的 SVG 不能执行脚本、不能加载外部
资源——这是浏览器自己的保证，比我们能写的任何 sanitizer 都强。另外在注册时拒绝
`<script>` / `<foreignObject>` / 外链 / `<image>`，目的**不是**安全兜底，而是让作者
**当场拿到报错**，而不是得到一个悄悄画不出来的图标。

## 决策四：接入要求 = 报告**任务语义**，不是报告**动作**

这是对接入方最重要的一条要求，也是最容易做反的。

**不要这样接**：

```
agent 自己决定：构建失败了 → 我让猫播 shake-head + 不爽
```

**要这样接**：

```
agent 报告：{ state: "failed", kind: "build", severity: "high" }
猫自己决定：→ 什么表情、什么动作、说不说话
```

原因有三个：

1. **用户能改。** 表情动作的映射是 `assets/reactions.json`，用户改完所有 agent 一起变。
   如果每个 agent 自己硬编码动作，用户就得去改每一个 agent。
2. **agent 不需要懂 49 个动作。** 它只需要知道自己在干什么。
3. **换皮不影响接入方。** 我们加动作、改动画，agent 一行不用动。

仍然允许直接驱动（`POST /control {"action": ...}`）——调试和特殊场合需要——
但那是**低层接口**，文档里明确标为不推荐日常使用。

任务事件的词汇表见 [`docs/19-agent-integration.md`](../19-agent-integration.md)。

## 决策五：桥必须鉴权

只监听 127.0.0.1 **不等于**安全。回环是网络边界，不是信任边界：以这个用户身份运行的任何进程
都能访问它——浏览器里的一个页面、一个沙箱进程、共享机器上的另一个会话。而这个桥能移动猫、
**读出用户积累的主人记忆**、往用户的配置目录写文件。

所以：首次启动生成 token，写进配置目录，权限 `0600`。能读到那个文件的东西本来就已经是这个用户，
读不到的（页面、别的账号、沙箱）现在被挡在外面。

agent 不需要被告知 token 的值——**读文件**即可，CLI 已经封好。`GET /health` 是唯一免鉴权的
接口，它只回答"我在跑"和"token 文件在哪"。

---

## 什么时候该改主意

- 如果出现**十几个** agent 同时接入，四档优先级会不够用，需要真正的调度器和公平性保证。
  现在的规模（2–3 个）用调度器是过度设计。
- 如果 agent 开始需要**长时间独占**（比如一个演示模式），需要显式的租约接口，
  现在的"按时长占用"不够表达。
- 如果用户要求**按 agent 静音**（"别让 CI 机器人动我的猫"），需要在注册表上加开关。
  这条成本很低，等有人真的要再加。
