# Desktop main-program prototype: architecture landed, a misdiagnosis, and the features that followed

2026-09-12 update: the user confirmed they saw the cat on a real screen, which proves that the previous record of "WKWebView content not appearing on screen" was in fact a **misdiagnosis** — the `screencapture` system screenshot tool used to check the result cannot capture any application window content in this environment (it cannot even capture normal windows such as Chrome and iTerm; it only captures the desktop wallpaper). The application was not actually failing to render. The original diagnostic process and the hypotheses already ruled out are kept below, as a troubleshooting record for this class of problem. The conclusion of this section takes precedence.

Additional work completed on that basis: replaced `device_query` with `NSEvent.mouseLocation`, which does not need Accessibility permission (this fixed both "cannot drag" and "cannot follow the mouse"; they had the same root cause); added a system tray (size steps, show/hide, a management popup, quit); replaced every icon with the `奶猫` (young cream kitten) avatar the user provided; added an intent channel to life-engine so an external "AI" can suggest a move target; built a local HTTP bridge (`packages/perception-contract`) so an external AI driver can read perception data and send intents, and verified the convergence with curl in practice. Details are in the new sections at the end.

The user explicitly asked to pause refinement of the cat model and turn to the "main program": a transparent desktop shell of Three.js + Tauri, supporting the model walking freely and following the mouse, and asked for a complete API and a sound architecture, using a placeholder model first to verify the pipeline. ## Architecture that has landed

The code is in `apps/lingxi/` (a Tauri v2 app) and three new `packages/`, corresponding to the module boundaries defined in [05-technical-architecture.md](05-technical-architecture.md):

| Module | Location | Status |
| --- | --- | --- |
| Desktop Shell | `apps/lingxi/src-tauri/src/lib.rs` | Implemented: monitor positioning, global mouse polling, click-through toggle, Accessibility permission check and system prompt |
| DesktopHost contract | `packages/desktop-host-contract/index.d.ts` | A pure type interface, zero dependencies; the host implementation is replaceable |
| DesktopHost implementation | `apps/lingxi/src/desktop-host.ts` | Implements the interface above with `@tauri-apps/api`. The only frontend file that directly references the Tauri SDK |
| Cat Life Engine | `packages/life-engine/src/index.mjs` | A pure state machine (idle/wander/follow_cursor/dragged), zero dependencies. All 6 unit tests pass (`node --test packages/life-engine/test/*.test.mjs`) |
| Renderer | `apps/lingxi/src/renderer.ts` | Three.js orthographic camera + a transparent WebGLRenderer. Implements mount/resize/render/hitTest of the `Renderer` contract |
| Placeholder model | `apps/lingxi/src/placeholder-cat.ts` ⚠️ **Deleted** | A "pixel cat" assembled from pure Box geometry, used to verify the pipeline, with no dependency on the Blender export pipeline. The current character is generated by the voxel skeleton in `apps/lingxi/src/rig/skeleton.ts`; animation is in `src/anim/` — this row is kept so the record of that time can still be read |
| Animation Director | `apps/lingxi/src/main.ts` | The only glue layer that knows both DesktopHost and LifeEngine/Renderer |

`packages/life-engine` and `packages/desktop-host-contract` follow the existing convention of `packages/contracts`: pure `.mjs`/`.d.ts`, no build step, imported by relative path, and not depending on npm workspaces that have not been set up yet.

## Parts that have been verified

- `node --test packages/life-engine/test/*.test.mjs`: 6/6 pass (the initial idle→wander transition, returning to idle on reaching the target, the mouse entering/leaving the follow radius, drag overriding autonomous behavior, and `setBounds` correctly shrinking the current position).
- The Rust backend compiles with `cargo check`/`cargo build` (using rustup's stable 1.98.1, because Homebrew's rust 1.87.0 cannot install this version of Tauri's dependencies, and `brew upgrade rust` would also require building `llvm@22` from source — [Tier 3, explicitly not recommended](https://docs.brew.sh/Support-Tiers#tier-3) — so `rustup override set stable` is used, which takes effect only in this project directory and does not touch the global default toolchain).
- Frontend TypeScript type-checking passes (`npx tsc --noEmit`). The cross-package import (`../../../packages/life-engine/...`) was solved by adding `server.fs.allow` to Vite.
- A debug-bridge command (`debug_log`, see lib.rs) confirmed the full startup chain: `main()` starts → the renderer mounts → `primary_monitor_bounds` correctly returns `{width:2940,height:1912,scaleFactor:2}` → `resize` correctly computes the logical size `1470x956` → the canvas exists and `getContext('webgl2')` succeeds → **the first frame's `renderer.render()` runs without an exception**, and the snapshot data is correct (`{state:"idle",position:{x:735,y:478},...}`).
- macOS Accessibility permission: `device_query` reading the global mouse position on macOS **does** require Accessibility permission (not the "keyboard only" assumption in the original document; verified by measurement and the code comment was corrected). Permission detection plus a system prompt dialog were added with `macos-accessibility-client`. When unauthorized, it degrades gracefully (skip mouse polling, do not crash). This was measured with a panic-then-fix approach.
- A real bug in the leg bones / window size, now fixed: the combination of `"visible": false` plus a manual `window.show()` makes AppKit report `is_visible()==true` and makes `set_size`/`set_position` "succeed", but the window **never appears in WindowServer's on-screen list** (confirmed by cross-checking with `CGWindowListCopyWindowInfo(kCGWindowListOptionOnScreenOnly)`). Changing the window to be visible by default, and not calling `show()` manually, makes the problem disappear — this fix is real, and it is kept in a code comment to prevent regression.

## Unsolved problem: WKWebView content does not appear on screen

**Symptom**: the app can start normally and become the foreground app (the menu bar shows the app name). The Rust side confirms the window is in WindowServer's on-screen list (`CGWindowListCopyWindowInfo` finds it, with the correct screen coordinates and `alpha=1.0`). The frontend JS confirms execution reached "first frame rendered" with no exception — but **no content actually appears on the screen**, including:

1. The production configuration (transparent background + the WebGL cat model)
2. A solid color (`renderer.setClearColor(0xff00ff, 1)`, opaque magenta)
3. Plain HTML (an opaque red `<div>`, with no WebGL involved at all)
4. The window configuration reduced to the plainest form (`transparent:false`, `decorations:true`, `alwaysOnTop:false`, `skipTaskbar:false`, `focus:true`) still does not display
5. Switching from `tauri dev` (`cargo run`) to a formal `.app` bundle launched with `open` gives the same result

**The most important diagnosis**: when the window appears in the on-screen list, capturing that window alone with `screencapture -l <windowID>` errors with `could not create image from window` — so this is not "the content is covered by something else" or "the transparency math is wrong". The window's actual render layer / backing store is **empty or invalid** as far as the screenshot system is concerned, even though WindowServer's window list considers it present and online.

Causes already ruled out:

- ~~Fur, leg bones, and other unrelated problems~~ do not apply; this is a brand-new app
- ~~A WebGL-specific problem~~ ruled out with a plain HTML `<div>`
- ~~Transparency making it "invisible"~~ ruled out with opaque magenta and opaque red
- ~~Some combination of `alwaysOnTop` / `skipTaskbar` / `visibleOnAllWorkspaces`~~ each was turned off and tested; the result did not change
- ~~`cargo run` starting a process directly, lacking a normal GUI session~~ ruled out by launching a formal `.app` bundle with `open` (on that path, `open -a Blender` in the same session displayed normally the whole time, which proves this environment itself can display a native GUI app)
- ~~A build cache causing old code to run~~ ruled out by checking that the process start time was later than the binary build time

Directions not yet verified, worth investigating next:

- Use Console.app or Instruments, under a graphical session, to observe this WKWebView process's Core Animation layer tree directly, instead of only indirect means such as `screencapture` / `CGWindowListCopyWindowInfo`
- Try an older or newer Tauri/wry version (the current `tauri = "2"` resolves to 2.11.5, `wry 0.55.1`) to see whether this version combination is a known problem
- Check whether this machine's GPU process (`com.apple.WebKit.GPU`) actually finished render compositing, and not merely that the log contains "didFinishLoadForFrame" (the page finishing load is not the same as compositing onto the screen)
- In a **real graphical login session**, launch the `.app` by double-clicking it manually (rather than calling `open` through any automation tool), to confirm whether it is related to the automation environment itself — although `open` has already ruled out "executing the binary directly", there could in theory still be a subtle session-permission difference between an `open` triggered by an automated shell and a user double-click

## Current state and what follows

The code architecture, the type contracts, the state-machine logic, and the Rust backend's handling of monitors, the mouse, and permissions are done, and they have passed tests that can be verified — this part is not "claimed complete"; there is evidence from unit tests and runtime checkpoints. The only thing stuck is the last step, "WKWebView content compositing onto the screen". That is a concrete, reproducible platform-level problem, not a bug in our own code logic (the application logic itself runs through to the end with no exception).

Until this problem is solved, it is not recommended to keep adding features to this app (expressions, skin switching, a task-observation UI, and so on) — that would only keep stacking assets on a window that cannot be seen, repeating a lesson this repository has already written down in the character-study chapters.

## Addendum: permission fix, tray, icons, AI perception interface (2026-09-12)

### Cursor tracking no longer needs Accessibility permission

`device_query` reading the mouse position on macOS also requires Accessibility permission (an earlier comment wrongly assumed only the keyboard needed it). That blocked both "follow the mouse" and "drag the cat" — because the two share the same "global cursor position" data, and the cursor was always `null`. After switching to `NSEvent.mouseLocation()` (an ordinary read-only AppKit class property; it does not involve event listening or event capture, and needs no authorization), both problems were solved together. The user has confirmed by measurement: the cat is visible, and click-through works. `macos-accessibility-client` stays in the dependencies, only for a future feature that truly needs authorization, such as "perceive global clicks/keystrokes".

### System tray

`build_tray` in `apps/lingxi/src-tauri/src/lib.rs`: three size steps (0.25x/0.5x/1x, mutually exclusive checks), `管理...` (Manage..., opens the management window), show/hide (the label switches dynamically), and quit. The app was changed to `ActivationPolicy::Accessory`, with no Dock icon; the tray is the only resident entry. `TrayState` is hosted with `app.manage()`. The three Tauri commands `set_scale` / `set_companion_visible` / `get_status` let the management window and the tray operate on the same state and stay in sync with each other (the CheckMenuItem/MenuItem handles used to change state are cloned wrappers of native objects, not duplicated data).

### Management popup

A new window `management` (`apps/lingxi/management.html` + `src/management.ts`): size selection, a show/hide button, and a display of Accessibility permission status. The Vite config was changed to a multi-entry build (`main` + `management`).

### Icons

The `奶猫` (young cream kitten) avatar the user provided (a downloaded file outside the `docs` directory, not checked in) was used to generate the full icon set: the app icon adds a soft gradient background and a drop shadow (so the ear tips are not clipped by the macOS rounded-rect mask when they sit against the edge), and the tray icon uses the cropped transparent version. The generation script was a one-shot Python/PIL run. The products were placed directly in `apps/lingxi/src-tauri/icons/` (`icon.icns`, `icon.ico`, and the PNGs at each size) and `apps/lingxi/public/icon.png` (used by the management popup).

### AI perception and drive interface

Two new zero-dependency packages, continuing the convention of `packages/contracts`:

- `packages/perception-contract`: type definitions. `ActivityEvent` (click / drag / cursor enter-leave / size change / show-hide), `ActivitySummary` (counts and durations over a rolling window; raw cursor tracks and keystrokes are not stored), `GrowthMetrics` (a v0 "engagement" score; the formula is rough, and the shape is stabilized first), `PerceptionSnapshot` (the full snapshot given to an external AI), `AIIntent` (the only thing an external AI can send: a suggestion to walk to a point, with an expiry).
- `packages/perception`: `createActivityRecorder()`, pure logic. All 4 unit tests pass (`node --test packages/perception/test/*.test.mjs`).

`packages/life-engine` gained `suggestMoveTo(point, now, holdMs)` / `clearIntent()`, and a new state `ai_directed`: its priority is below "the user is dragging" and above "autonomous wander / follow". It expires on its own, and will not trap the cat in "AI mode" with no way out. Covered by 3 new unit tests (the suggestion takes effect, drag always wins, and it recovers automatically after expiry). All 9 tests pass.

The Rust side starts an HTTP bridge for this machine only (`tiny_http`, synchronous, zero async-runtime dependency, listening only on `127.0.0.1:47811`, not on `0.0.0.0`):

- `GET /perception`: the latest `PerceptionSnapshot` (the frontend pushes it to the Rust cache every 2 seconds, via the `report_perception` command).
- `POST /intent`: the body is `AIIntent` JSON, forwarded as an `ai-intent` event to the frontend, and fed to `suggestMoveTo`.

**Convergence was verified with curl in practice**, not as a paper design:

```sh
curl -X POST http://127.0.0.1:47811/intent -H "Content-Type: application/json" \
  -d '{"targetPoint":{"x":50,"y":900},"holdMs":10000,"reason":"convergence test"}'
```

Then three consecutive `GET /perception` calls: `petState` stably shows `ai_directed`, and `petPosition` moves from `(153,155)` → `(138,262)` → `(114,440)`, smoothly toward `(50,900)` — the chain from an external HTTP request to the cat actually moving on the desktop ran through end to end, and there is evidence.

### An honest list of what is not done yet

- Global click/keystroke perception ("what the user clicked somewhere else"): that needs real event listening, which still requires Accessibility permission. Not done.
- `packages/perception` currently records only clicks/drags that land on the cat, not global activity.
- The look of the tray / management window / icons was not verified with screenshots this round (stuck on the same screenshot-tool limitation). The user needs to look once and confirm whether it looks good and whether the placement is right.
- The growth/engagement scoring formula is a placeholder. The product-layer design of "how the cat grows with the user's behavior" is still in [04-life-engine.md](04-life-engine.md), and has not been aligned back onto this version of the code.
- The HTTP bridge has no authentication (it assumes the trust boundary "only a process on this machine can connect to 127.0.0.1"). If an untrusted external driver is connected later, another layer is needed.

## Addendum: the architecture compared with open-source references (2026-09-12)

Several open-source projects of the same kind were looked at, as a reference for the question "is the architecture optimal", rather than judging it from nothing:

- [CrabNebula: Building a Desktop Pet with Tauri](https://crabnebula.dev/blog/building-a-desktop-pet-with-tauri/) — a tutorial project of the same type, written by Tauri's official ecosystem team.
- [gonzalovsilva/Shimeji-ee](https://github.com/gonzalovsilva/Shimeji-ee) (and [Kilkakon's affordances document](https://kilkakon.com/shimeji/affordances.php)) — the oldest and most mature open-source implementation of the desktop-pet category (Java), with an extremely rich behavior library.
- [AkshitIreddy/AI-Desktop-Pet](https://github.com/AkshitIreddy/AI-Desktop-Pet) — positioned almost the same as our end goal: an "AI-driven desktop pet". It likewise uses Rust for the screen, windows, and cursor, and likewise emphasizes a privacy boundary.
- [iiviie/cursor-pets](https://github.com/iiviie/cursor-pets), [SeakMengs/WindowPet](https://github.com/SeakMengs/WindowPet) — lighter Tauri desktop pets, with a feature set close to this version of ours (follow the cursor, click-through, drag).

**What we have already got right, in the same vein as these projects:**

- Transparency + alwaysOnTop + `set_ignore_cursor_events` for click-through is the standard Tauri desktop-pet solution. The CrabNebula article explicitly says "there is no ready-made config item; you have to implement it yourself in Rust" — our approach is fully on that path.
- The Rust side polls the cursor and sends events to the frontend; the frontend only handles position state and animation — CrabNebula's project and ours have the same division of labor (although they use the `mouce`/`mouse_position` crates and update position only on click, with a CSS transition for smoothing; we poll `NSEvent.mouseLocation` continuously, and life-engine does the real per-frame displacement, which is finer).
- One shared fullscreen transparent window carries the character, rather than one window per character — AI-Desktop-Pet's documents explicitly say they refactored from "one Electron window per pet" to "one shared window". We started with that design, and do not have to walk it back.
- The AI is given only one convergent intent channel (rather than opening an interface for every capability) — this is the same idea as AI-Desktop-Pet's "skill wheel", at a different scale: they have already grown to 22 named skills; we currently have only two, "move to a point / switch mode", but the design is the same extensible shape (add fields to `AIIntent`, do not add endpoints).

**Gaps worth recording, but not worth acting on now (a reference if there is a long-term investment later):**

- **Window awareness ("walk on other apps' windows")**: Shimeji's affordances and AI-Desktop-Pet both support the cat walking along real window edges / sitting on windows. We currently know only the overall desktop size, not where other windows are. It is technically feasible — while investigating the tray problem this round, `CGWindowListCopyWindowInfo` was already used to confirm that other processes' window positions and stacking order can be read. That information has just not been connected into life-engine yet.
- **Data-driven behavior definitions**: Shimeji splits "when to do what" (behaviors.xml) and "how this action is specifically performed" (actions.xml) into externally editable config files, so a non-programmer can add a new behavior or a new skin. Our split of those two layers is right (life-engine decides the state, the Renderer decides how it is performed), but both are hardcoded in TS/JS. At this stage (still verifying the pipeline; the model is still placeholder boxes) hardcoding is fine. After the real model and more behaviors ship, it is worth making the "behavior trigger conditions" layer data-driven.
- **AI intent vocabulary**: `AIIntent` currently has only "where to walk + switch mode". Once AI decision-making is really connected, it will very likely need the skill-wheel kind of "an action you can name" (for example "sleep", "dance", "greet"). At that point add an optional `skill` field on `AIIntent`, rather than opening a new channel — consistent with the existing design principle, not a rewrite.
- **A privacy mode for "giving the AI a little screen perception"**: AI-Desktop-Pet's "screen vision" feature works as "the user turns it on manually for a short time, it expires automatically, and frames are not stored". That sense of proportion is fully consistent with the privacy boundary already written in `perception-contract` ("no cursor track is kept, no keystrokes are kept"). If a heavier perception such as "let the AI see the screen" is really built later, this is a ready-made, already-tested reference for the proportion.

**Conclusion**: the existing module split (Desktop Shell / Life Engine / Renderer / Perception), the single-window plan, the division of labor of Rust-polls + frontend-state-machine, and giving the AI only one extensible intent channel — these foundational architecture decisions are consistent with open-source projects of the same kind. They were not decisions we simply assumed. The gaps listed above are extension points that need to move only "when more behaviors / more AI capability grow later". They are not something that should be torn down and redone now.

## Addendum: the tray's three-piece set, completed — settings persistence and startup-state sync (2026-09-12)

### State before this round

The tray (three size steps / show-hide / `管理...` (Manage...) / `逗猫模式` (tease-the-cat mode) / quit), the management popup (`management.html`), and the four commands `set_scale` / `set_companion_visible` / `set_interaction_mode` / `get_status` were already implemented, and the tray and the management window stay in sync through the same `TrayState`. But there were two gaps that made it "not feel finished in use":

1. **Settings are not persisted**: size / visibility / mode all live in memory, and a restart returns to the defaults (1x, shown, `日常` (everyday)).
2. **A startup-state sync gap**: the frontend updates size only by listening for the `set-scale` event, while any Rust-side broadcast of "set state at startup" happens before the webview finishes loading — the event is necessarily lost. The symptom: the tray's checked state and the cat's actual size can disagree (as soon as persistence is introduced this fires immediately: the tray checks `小` (Small), but the cat renders at 1x).

### Changes this round

- `src-tauri/src/lib.rs`: added `PersistedSettings` (`version/scale/visible/mode`). The path is `settings.json` under the application config directory (on macOS, `~/Library/Application Support/com.dushaobin.lingxi-desktop/`). Every `apply_scale` / `set_visible` / `apply_mode` on `TrayState` also writes to disk (a tmp file + rename, so a crash does not leave half a file). Setup loads and restores it. Bad data (a hand-edited scale/mode) falls back to the defaults, rather than producing a cat whose size is 0.
- `src/main.ts`: on startup it actively pulls the authoritative state once with `get_status` and applies it to the renderer and life-engine. It no longer depends on "a broadcast event that might have been missed".
- The test module in `src-tauri/src/lib.rs`: 5 unit tests cover — a missing file falls back to the defaults, a path of None falls back to the defaults, an illegal scale/mode is rejected while visible passes through normally, the three tray steps round-trip exactly, and a write in the real on-disk form (pretty JSON + tmp/rename) reads back completely.

### Verification

- `cargo test`: 5/5 pass. Note that in this machine's sandbox shell, PATH hits Homebrew rust 1.87 first, and these dependencies require rustc ≥ 1.88. `export PATH="$HOME/.rustup/toolchains/stable-aarch64-apple-darwin/bin:$PATH"` is needed before running cargo — a directory-level `rustup override` takes effect only for the rustup proxy, and does not cover the case where cargo resolves `rustc` again internally.
- `npx tsc --noEmit` passes; `npm run build` passes, and both entries `dist/index.html` and `dist/management.html` are produced.
- `node --test packages/...` stays 17/17 (this round did not touch the pure-logic packages).
- Evidence on a real machine: after `tauri dev` detected the Rust change and restarted the app automatically, `settings.json` was written with the correct schema (the default values), which shows the persistence write path has executed inside the real startup flow.
- **Still needs the user to confirm by eye**: the tray menu appears and the checks are correct; after switching size the cat changes live and the choice survives a restart; after hiding, the tray's `显示` (Show) can find the cat again; the `管理...` (Manage...) popup can open and its controls stay linked with the tray. The screenshot tool in this environment cannot capture window content (see the misdiagnosis record at the start of this document), so these items can only be accepted by eye.

## Addendum: the real root cause of "not on screen + the tray disappears" — how it is launched (evening of 2026-09-12)

### User acceptance result

After launching the packaged `.app` with `open`, **the user confirmed on the spot: the cat was on screen, and the tray icon was there too**. The persistence restore path (`settings.json` is read and applied at startup) also executed inside the real startup flow.

### Root cause: a bare binary vs the packaged .app

The earlier "misdiagnosis" conclusion was only half right (`screencapture` really is broken), but it covered up the real problem — **on this machine (macOS 14.6, tauri 2.11.5 / wry 0.55.1), when the app is run as a bare binary (`cargo run` / `tauri dev` running `target/debug/desktop-shell` directly)**:

- The window is in WindowServer's on-screen list, `alpha=1.0`, full size — but the WKWebView content **never composites into an image**;
- `TrayIconBuilder::build()` reports no error, and the in-process NSStatusItem is created successfully — but the corresponding status-bar icon **never appears** on screen.

After `tauri build --debug` produced `Lingxi Desktop.app` and it was opened with `open` (through LaunchServices, started in a real GUI session), both problems **disappeared at the same time**. That is, the originally recorded "WKWebView content does not appear on screen" was a launch-method problem from the start, not a Tauri version bug and not a rendering-code bug. The time "the user confirmed they saw the cat" must have been a packaged launch, or an instance in a different context.

### A reusable way to verify (screencapture is unusable in the sandbox environment)

Ask WindowServer directly with the system Python's Quartz. **No screenshot, and no permissions:**

```python
import Quartz
wl = Quartz.CGWindowListCopyWindowInfo(Quartz.kCGWindowListOptionOnScreenOnly, Quartz.kCGNullWindowID)
# Normally you should see a layer-5 full-size window with owner="Lingxi Desktop" (alpha 1.0),
# and a layer-25 status-bar item; when the tray did not register, the latter is simply absent.
```

This round used it to tell apart two different problems: "the window is there but the content is empty" (layer 5 is present, alpha 1) and "the tray never made it onto the screen" (we are not in the layer-25 list).

### Practical impact on day-to-day development

- **The development loop should use `npm run tauri build -- --debug` + `open target/debug/bundle/macos/Lingxi Desktop.app`**, not `tauri dev` — the latter, in bare-binary form, shows nothing, and makes people think the code is broken. A debug bundle reuses already-compiled products, and a version comes out in a few tens of seconds.
- The DMG step of `tauri build` (`bundle_dmg.sh`) fails on this machine, but the `.app` has already been generated before that, so development verification is unaffected. Only external distribution needs the DMG fixed later.
- For this kind of tray/WebView symptom, "succeeded inside the process, disappeared on screen", first use the Quartz check above to tell "not created" from "created but not on screen", and then decide where to look.

### Additional change: show the Dock icon + install to /Applications (evening of 2026-09-12, accepted by the user)

- `ActivationPolicy::Accessory` → `Regular` (the user asked that "it be shown in the Dock while running", overturning the earlier product decision that "the tray is the only resident entry"). Also added handling of `RunEvent::Reopen`: when the Dock icon is clicked, if the cat is hidden, call `set_visible(true)` to bring it back, on the same `TrayState` path as the tray's show/hide, so the check and the label stay in sync. The tray is still the main control surface; the Dock icon is a second entry.
- `Lingxi Desktop.app` has been installed to `/Applications` (the sandbox refused a write outside the workspace; it was completed by elevating permissions according to the process). After that, day-to-day use can open it from Launchpad / Spotlight / the Dock, without `open` on the bundle path.
- Measured after launching from /Applications: the layer-25 tray item is on screen (34×37 @ x=974), the layer-5 cat window is on screen at full size (alpha 1.0), and `NSWorkspace` reports `activationPolicy: 0 (Regular)`, meaning the Dock icon is normal. WKWebView's three helper processes, Networking / WebContent / GPU, are accessory as expected, and do not affect the Dock.

### Addendum: behavior correction for tease-the-cat mode / work mode (2026-09-13)

The user reported three points, which point at the same root cause:

1. "In `逗猫模式` (tease-the-cat mode), it goes and finds the mouse position on its own" — that is, `逗猫模式` does not actively chase the cursor. A chase is triggered only when the cursor happens to come near the cat (within `followRadius` = 220). When the cursor stays far away, the cat just idles and wanders as usual.
2. "In `工作模式` (work mode), it goes to the edge on its own and does not affect the main visual point" — work mode does not stably "stay at the edge". The previous "yield" fired only while `userBusy` was true (the cursor had moved within the last 1.5 seconds). When the mouse is still, the cat may stay in the middle of the screen.
3. "Up, down, left, and right seem unable to move to an edge position" — even when a yield or a wander is triggered, the target is "one hop from the cat's current position, at a random angle, within `wanderRadius` (260 px)". On a screen clearly larger than that radius, the random wander is not large enough and the direction is unstable, so in practice it is very hard to actually reach any edge.

The root cause is the same: in `packages/life-engine/src/index.mjs`, the wander/yield target was never a coordinate "anchored to the workspace boundary". It was "a small-radius random hop starting from the current position". The `逗猫` (tease-the-cat) chase was blocked by a distance threshold (`followRadius` / `followReleaseRadius`), and took effect only when the cursor was already very close.

Changes (all in `packages/life-engine/src/index.mjs`):

- **`逗猫模式` (tease-the-cat mode)**: remove the `followRadius` / `followReleaseRadius` distance thresholds. As soon as cursor coordinates are available (however far), enter `follow_cursor` immediately and chase. Return to `idle` only when the cursor signal is completely lost (`cursor === null`, for example when it leaves the screen).
- **`工作模式` (work mode)**: add `pickEdgeRestTarget(cursor)`, which anchors the target directly to a corner of the workspace (x is `margin` or `width-margin`, y is `margin` or `height-margin`, choosing the corner opposite the cursor's quadrant), rather than hopping a random distance from the current position. Idle-to-wander, a wander target being used up, and the cursor approaching the current position or the target all use this function, and the old `userBusy` gate ("the cursor moved in the last 1.5 seconds") is removed — in work mode, whether or not the cursor is currently moving, as soon as it gets close to the cat the cat moves to the opposite corner. The landing point of default idle/wander is also always one of the four corners, and it can no longer stop in the middle of the screen.
- Because the target is the boundary coordinate itself (rather than "a random hop that happens to land near the boundary"), point 3's "cannot reach the edge" is solved along with it — these are not two independent fixes; they are two manifestations of the same change.

Verification: `packages/life-engine/test/life-engine.test.mjs` was updated and all of it passes (`node --test packages/life-engine/test/*.test.mjs`, 20/20). Five cases were added or rewritten specifically to cover these three points (tease-the-cat mode chases immediately from far away; during a tease-the-cat chase, the cursor moving farther away still does not break the chase; in work mode, when the cursor approaches, the cat retreats to a corner rather than following; when idle turns into wander the target is a real far-corner coordinate; over a whole wander it can actually reach the boundary coordinate rather than stopping halfway). `npx tsc --noEmit` (`apps/lingxi`) passes. This round touched only the pure logic of `packages/life-engine`, not the Rust or rendering layer, and `cargo test` was not re-run.

**Still needs the user to confirm by eye on a real machine**: in work mode, whether the cat really stays stably near the four corners (rather than somewhere that does not match intuition), and in tease-the-cat mode, whether the chase speed and feel are natural — those two cannot be verified for look-and-feel in a headless unit test, and can only be accepted by eye.

### Addendum: the real root cause of "cannot reach the edge" — renderer coordinate mapping, not only life-engine (2026-09-13)

The user confirmed the previous round's three judgments (`followRadius` as a distance threshold really is meaningless, "the edge" means the physical edge of the screen, and the motive is "I don't want to be disturbed while working"), but also pointed out that "cannot move to the edge" still needs work. A fresh check found: the previous round fixed only life-engine's *logical* target (it now really does compute "a corner coordinate against the margin"), but the formula in `apps/lingxi/src/renderer.ts` that converts that logical coordinate into a Three.js world coordinate is itself buggy. When the logical coordinate reaches the boundary, the picture does not follow it there — that is the problem this round actually has to fix. The life-engine fix is the necessary but not sufficient half.

**Root cause**: rendering uses an orthographic camera with a downward tilt (`position (0,1.4,2.6)`, `lookAt (0,0.4,0)`). In the previous conversion `cat.root.position.x = px * unitsPerPixelX` (and the same for z), `unitsPerPixelX` is the pixel scale corresponding to "the whole frustum half-width", but the range of `px` (the logical coordinate's offset from the screen center) is only `±width/2` — only half of the frustum half-width itself — so the cat can walk at most to half the frustum width. The vertical direction is worse: the camera has a downward tilt, and a world-Z displacement is "squashed" by that tilt when projected onto the screen's vertical axis (shrunk to about 0.36×). That compression was not considered by the conversion formula at all. An independent numerical check (a Node script, pure vector math, not depending on three.js) reproduced the magnitude of both problems: **when the logical coordinate has already reached the rightmost/leftmost edge of the screen, the picture has only reached 50% of the viewport width; when it has reached the top/bottom edge of the logical coordinate, the picture has only reached about 18% of the viewport height** — this fully explains "up, down, left, and right seem unable to move to the edge", and it explains why "up and down" feels more obvious than "left and right" (0.18 is far smaller than 0.5).

**Fix**: stop converting position with the frustum's "overall scale". Instead, solve backward from the camera's real orientation: "on the ground plane, how far should the world coordinate move for one pixel along the screen's left-right / up-down direction" (`groundRight` / `groundUp`, obtained from the cross product of vectors computed from the current `camera.position` / `lookAt`, not magic numbers copied by hand). From that, define the new `worldPerPixelX` / `worldPerPixelZ` and replace the old conversion. Two other places hit by the same problem were fixed along with it: the facing angle `facingAngle` (it used to take `atan2(dx,dy)` directly on logical pixels, which happened not to be wrong when the two axes used the same scale; once the scales differ, it must be converted into world coordinates before the angle is taken, or the body facing drifts when walking diagonally), and the head's `desiredYaw` toward the cursor (the same reason, and it is compared as a difference against `facingAngle`, so the two are meaningful only under the same coordinate convention).

**How it was verified**: this is a pure geometric-conversion bug, and it cannot be covered by `node --test` (there is no runnable WebGL/DOM environment). An independent numerical script was used instead, running both the old and the new formulas and comparing them with the expected NDC boundary (±1), confirming that after the fix they land exactly on the boundary (before: right edge 0.5, bottom edge −0.18; after: right edge 1.0, bottom edge −1.0, and the same for the left/top edges). `npx tsc --noEmit` and `npm run build` both pass. **This is still only "it should be right" geometrically. Whether the cat sits against the edge of a real window in a way that looks good, and whether the path it walks is smooth, still has to be confirmed by the user looking at it once** — this project has already had cases of "numerically correct but visually unappealing" (the leg-bone and fur rounds), and this one numerical check cannot be treated as the final close.
