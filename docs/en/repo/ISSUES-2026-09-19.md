## Interface requirement: the load / query / switch loop for custom assets

> Raised on 2026-09-19. This is not a bug. It is a **capability gap**: custom assets (skins, actions, expressions, bubbles)
> are available to the user and unavailable to an agent. Below is the interface surface that needs to be filled in.
>
> Related concrete defects: #3 (a misspelled `action`/`expression` is not reported),
> #13 (a custom skin can be loaded but cannot be selected), #14 (reload has no API entry).

### Background

The user's goal is "let an agent drive the whole cat". Custom assets are the most direct piece of that goal —
the user defined actions, expressions, and skins themselves, and reasonably wants the agent to be able to use them too.
But today each of the three links is broken in one place:

| Link | Current state | Gap |
|---|---|---|
| **Load** | Only the button `主界面 → 外观 → 重新加载自定义资源` (main window → Appearance → Reload custom assets) | After an agent edits a file it **cannot make the change take effect**, and it cannot read the validation errors |
| **Query** | `GET /capabilities` lists the dynamically merged catalogue ✅ | Missing a **source mark** (which ones are custom), so an agent cannot tell which are the user's |
| **Switch** | Custom **actions/expressions** can be driven (forwarding is allowed); custom **skins** are rejected by a hard-coded list | Skins cannot be switched at all; the validation of actions/expressions is fake |

### Requirement 1 — Load: there must be a trigger an agent can reach

Implement either one (the first is recommended, and it matches the style of the existing fields):

```bash
# Plan A: reuse /control
POST /control  {"reloadAssets": true}

# Plan B: a separate endpoint
POST /assets/reload
# or the MCP tool lingxi_reload_assets
```

**The response body must include the validation result** (this is the point; today there is none at all):

```json
{
  "ok": true,
  "loaded": { "actions": 53, "expressions": 40, "skins": 10, "bubble": true },
  "source": { "actions": "custom", "expressions": "custom", "skins": "merged", "bubble": "custom" },
  "errors": []
}
```

On failure (some files are illegal, and the rest still take effect — keep the existing "each file is independent" design):

```json
{
  "ok": false,
  "loaded": { "actions": "builtin", "expressions": "custom", "skins": "merged", "bubble": "builtin" },
  "errors": [
    "actions.json：wb-deploy 轨道必须从 0 开始，在 duration 结束并归零",
    "bubble.json：borderWidth 需要在 0–12 之间"
  ]
}
```

**Hard requirement: `errors` must be returned to the caller as-is.** Today `AssetErrorState` is exposed only through a Tauri command
to the management window (`lib.rs:1615-1626`). An agent can only rely on the user repeating what they see.

### Requirement 2 — Query: it must be possible to tell "built-in" from "custom"

`GET /capabilities` already returns the dynamic catalogue, but each item lacks a source. Add it:

```json
{
  "actions":     [{ "id": "wb-deploy", "name": "部署上线", "category": "特效", "duration": 3.5, "source": "custom" }],
  "expressions": [{ "name": "绿灯", "source": "custom" }],
  "skins":       [{ "id": "workbuddy-mint", "name": "青釉工蜂", "source": "custom" }]
}
```

`部署上线` is the action name ("ship the deploy"), `特效` is the category ("effect"), `绿灯` is the expression name ("green light"), and `青釉工蜂` is the skin name ("celadon worker bee").

**Why this matters**: `expressions.json` and `actions.json` are **replaced wholesale**.
If an agent wants to copy a built-in action and tweak it, it must know whether that action is still built-in or the user has already changed it —
otherwise it may overwrite the user's edits.

Also suggested: a read-only status endpoint:

```bash
GET /assets/status
# → { "dir": "...", "lastLoadedAt": 1789780000000, "lastErrors": [],
#     "active": { "actions": "custom", "expressions": "custom", "skins": "merged", "bubble": "custom" } }
```

### Requirement 3 — Switch: a skin must accept any id in the dynamic catalogue

```bash
POST /control  {"skin": "workbuddy-mint"}    # a custom skin → 400 today, required to be 200
```

How to change it: replace the `skin` check inside `apply_control_command`, which uses the hard-coded `KNOWN_SKINS`
(`lib.rs:94-108`), with `CapabilitiesState.latest` reported by the renderer.
The same for `expression` — and **the current false success must be fixed in the other direction**: a misspelled id must be reported as an error,
rather than returning `applied: ["... (forwarded)"]`.

```rust
// pseudocode
let caps = state.latest.lock().unwrap();                       // CapabilitiesState
let known = caps["skins"].as_array().map(|a| a.iter()...)      // take it from the dynamic catalogue
// ⚠️ when the table is empty (the webview has not reported yet) it must degrade to "allow", and must not kill a valid id by mistake
```

**Note that `camera` is different.** There are a fixed 6 cameras (`KNOWN_CAMERAS`, `lib.rs:109`).
They do not change with custom assets, so hard-coding is reasonable. Suggested: mark it
`"fixed": true` in capabilities, explaining why it does not come from the dynamic catalogue — otherwise the next person will think it is the same bug.

### Acceptance criteria

Nothing outside the code changes. All of it can be run with HTTP alone:

```bash
# 1. Load: the agent triggers it itself, and can read the result
curl -s -X POST localhost:47811/control -d '{"reloadAssets":true}'
# → ok and errors is empty; after deliberately breaking one file → ok=false and errors says which action is wrong

# 2. Query: sources can be distinguished
curl -s localhost:47811/capabilities | jq '.skins[] | select(.id=="workbuddy-mint")'
# → {"id":"workbuddy-mint","name":"青釉工蜂","source":"custom"}

# 3. Switch: a custom skin can be selected
curl -s -X POST localhost:47811/control -d '{"skin":"workbuddy-mint"}'
# → 200 {"applied":["skin=workbuddy-mint"],"ok":true,"rejected":[]}

# 4. Switch: a misspelled id must error (not a false success)
curl -s -X POST localhost:47811/control -d '{"skin":"nope","action":"nope","expression":"nope"}'
# → 400, and all three fields appear in rejected
```

Once these four have been run, the skill in `~/.workbuddy/skills/lingxi-desktop-cat/` can write
"custom assets" as one complete agent workflow, instead of only being able to teach the agent
"you cannot do this; go ask the user to click the button".

### Field note (2026-09-19 09:15, after custom assets were loaded)

The user clicked `重新加载自定义资源` (Reload custom assets) in the UI, and the assets **were confirmed merged and in effect**:
`GET /capabilities` → `skins` 10 items (9 built-in + `workbuddy-mint`),
`actions` 53 items (49 + 4 `wb-*`), `expressions` 40 items (30 + 10).

Retested item by item under that precondition. The results follow — **skins are confirmed outright, and actions clarify a misjudgment**:

| Capability | Request | Result | Verdict |
|---|---|---|---|
| Custom skin | `{"skin":"workbuddy-mint"}` | `400 unknown theme "workbuddy-mint" (see GET /capabilities)` | ❌ **#13 confirmed**. And the endpoint it tells you to check has just listed this id |
| Built-in skin (control) | `{"skin":"moon-oat"}` | `200 applied:["skin=moon-oat"]` | ✅ Normal |
| Custom expression | `{"expression":"绿灯"}` | `200 applied:["expression=绿灯 (forwarded)"]` | ⚠️ Cannot be confirmed — see below |
| Custom action | `{"action":"wb-suspend"}` | `200 (forwarded)` + sampled `action=wb-suspend` for 4.5s | ✅ **Really played** |
| Built-in action (control) | `{"action":"paw-wave"}` | `200` + sampled `action=paw-wave` | ✅ Normal |

#### Clarification one: custom actions really work, but the sample has to be read correctly

The first time `wb-deploy` was tested, the sample window only showed the built-in `meow`, which once looked like "forwarded but not played".
A control experiment overturned that judgment: **the cat was in `wander` at the time**, and `wb-deploy` was deferred until it stopped
(this is recorded, established behavior). After switching the test to the longer `wb-suspend` (4.5s),
the `action` field of `/perception` stayed `wb-suspend` the whole way.

→ **The forward path works for custom actions.** The lesson is: the `action` in a single sample may be the **previous**
autonomous action, and it cannot be used to judge this attempt a failure. This is the same line as the skill's "an action has a delay; do not assume it failed and send it again".

#### Clarification two: a custom expression cannot be confirmed through the interface, and that is the direct cost of #6

Forwarding `expression` returns 200, but `/perception` **does not expose the current expression** (item 6.1),
so whether it is a built-in expression or a custom one, **the driver cannot confirm that its own change succeeded**.

That means the false-success risk of #3.1 is **undetectable** for expressions: a misspelled expression and a correct one
return the identical `200 (forwarded)`, and no field on the observation surface can tell them apart.
30 built-in + 10 custom, 40 expressions in all, and the driver is **completely flying blind**.

→ Filling in #6 (`/perception` exposes `expression`) is not a nice extra for observability.
It is the precondition for whether #3.1 can be noticed.

## 13 [medium-high] Custom skins: all four doors are shut, and neither the user nor an agent can reach them

> Dug into on 2026-09-19 09:20. It started because the user clicked `重新加载自定义资源` (Reload custom assets) and reported "I don't see it",
> and suspected the assets were written to the wrong directory ("they should go under the installed application, not under the source").
>
> **Conclusion: the directory is right. The user's suspicion pointed at a real pit, but the real cause is somewhere else — and it is more serious.**

### Ruled out first: the asset location is completely correct

| Check | Evidence |
|---|---|
| Which version is running | `lsof -p 46074` → `/Applications/灵犀.app/Contents/MacOS/lingxi` — **it is the installed build** |
| Which directory it reads | The same bundle id `com.dushaobin.lingxi-desktop` → `~/Library/Application Support/com.dushaobin.lingxi-desktop/` |
| Were the assets actually read | `GET /capabilities` lists `workbuddy-mint`, 53 actions, 40 expressions ✅ |
| Did it pollute the source tree | `git status --short` shows only `ISSUES-2026-09-19.md` — **zero pollution of the source tree** |

**The installed build and the build from source share the same bundle id, so their `Application Support` directories are the same one to begin with.**
Putting assets inside the `.app` bundle is the wrong move — the next build would overwrite them. The correct location for runtime custom assets
is (and can only be) `Application Support/<bundle-id>/assets/`. That part of the current state is fine.

### The real cause: the appearance page does not read custom assets at all

`apps/lingxi/src/management.ts`:

```ts
line 16:  import skinCatalogue from './data/skins.json';   // ← statically packed at compile time
line 27:  const SKINS = skinCatalogue as SkinCard[];
line 202: ...SKINS.map(...)                                 // ← cards are generated only from this array
line 224: card.addEventListener('click', () => invoke('set_skin', { skin: skin.id }));
```

`apps/lingxi/src/data/skins.json` has only **9 built-in skins and no custom items**,
and it is packed into `dist/` at build time (measured: `grep -r workbuddy-mint apps/lingxi/dist/` and
`/Applications/灵犀.app/` **find nothing**).

**So no matter how many times you click `重新加载` (Reload), `青釉工蜂` (celadon worker bee) will not appear on the appearance page — the card is simply not on the UI.**

### The four doors: even if it appeared on the UI, it still could not be used

| # | Door | Location | Behavior |
|---|---|---|---|
| 1 | Card list on the appearance page | `management.ts:202` reads the static `data/skins.json` | A custom skin **does not generate a card**, so the user cannot see it |
| 2 | UI click → `set_skin` | `apply_skin` at `lib.rs:399` | `KNOWN_SKINS.contains` fails → **silently falls back to `DEFAULT_SKIN`**, with no notice |
| 3 | HTTP/MCP → `/control` | `lib.rs:865` | `KNOWN_SKINS.contains` fails → **400** (and the error message contradicts itself) |
| 4 | Restore on startup | `lib.rs:266` | `settings.json.skin` is not in `KNOWN_SKINS` → falls back to `default_skin()` — **even if it was set, it does not survive a restart** |

The comment on `apply_skin` says "An unknown id falls back rather than erroring, because settings.json
outlives any particular asset list" — that design intent is right for **built-in skins** (so a deleted
skin does not stop the app from starting), but it kills **custom skins** along with them, and door 2 is **silent**:
the user clicks a card and gets no feedback, and only feels "clicking did nothing".

### Net result: `workbuddy-mint` is an asset that is "loaded but nobody can reach"

| Asset | Can the user use it | Can an agent use it | Is there a visible entry |
|---|---|---|---|
| Custom **skin** `workbuddy-mint` | ❌ | ❌ | ❌ **Reachable by nobody** |
| Custom **actions** `wb-*` (4) | ❌ (no manual trigger) | ✅ Can be played (measured: `wb-suspend` succeeded) | ❌ and `category:"特效"` (effect) is never auto-played |
| Custom **expressions** (10) | ❌ | ⚠️ The request succeeds but cannot be verified | ❌ |

**That is the complete explanation of "I clicked reload and did not see it"**: the reload **did take effect** (actions can play, capabilities are updated),
but none of the three things has a **user-visible entry** — the skin does not even generate a card, the actions are in the effect category and will not play themselves,
and there is no UI that can show the expressions. The only feedback the user can see is the small `asset-status` line `已重新加载。` (Reloaded.)

### A gap between a UI promise and reality

`management.html:225` says:

> 动作、表情、主题都是可编辑的 JSON 文件，放在应用配置目录的 `assets/` 里，改完点「重新加载」即可生效
>
> (Actions, expressions, and themes are all editable JSON files, placed in `assets/` in the app config directory. After you edit them, click "Reload" and they take effect.)

For **actions/expressions** (on the agent side) that mostly holds; for **themes** it does not hold at all —
there is no entry to select one, and all four doors are in the way. That sentence makes the user think "once I edit it I can use it",
and the actual result is "I edited it, reloaded, and then nothing happened".

### Direction of the fix (not implemented)

**Minimum that works**: change the appearance-page card list to the union of "the 9 built-in skins + the custom skins read from `get_custom_assets`"
(`install_asset_templates` already passes `skinCatalogue` from TS to Rust; the reverse direction is equally possible).

**Complete**: replace the `KNOWN_SKINS` check on doors 2/3/4 with `CapabilitiesState.latest` reported by the renderer
(the same thing as "requirement 3" in the interface-requirement section),
and **an empty table must degrade to allow**, or ids will be killed by mistake before the webview reports.
Door 4 also needs its own consideration: at startup the renderer has not reported yet, so it cannot be validated — suggested change:
"restore from `settings.json` first, and fall back later if the id does not exist once the renderer has reported".

**Along the way**: the silent fallback in `apply_skin` should at least emit an event so the UI can say
`该主题不存在，已回到默认` (that theme does not exist; returned to the default).

## 1 [high] `/intent` has no input validation → NaN makes the cat disappear

### Reproduction

```bash
curl -s -X POST http://127.0.0.1:47811/intent \
  -H 'Content-Type: application/json' -d '{"targetPoint":{}}'
# → {"ok":true}

curl -s http://127.0.0.1:47811/perception
# → {"petPosition":{"x":null,"y":null},"petState":"ai_directed", ...}
```

**The cat disappears from the desktop.** The interface returns `ok:true` the whole way.

### Root-cause chain (confirmed by reading the code)

1. `apps/lingxi/src/main.ts:340-341` only checks `if (targetPoint)` — an empty object `{}` is truthy,
   and it is passed straight through to `engine.suggestMoveTo(targetPoint, ...)`.
2. `packages/life-engine/src/index.mjs:727-734` wraps it with
   `clamp(targetPoint.x, minX(), maxX())`. **But this layer of "defensive clamp" is completely useless against non-finite input**:

   ```js
   function clamp(value, min, max) { return Math.min(Math.max(value, min), max); }  // index.mjs:121-123
   // Math.max(undefined, 24) → NaN, and clamp passes NaN through as-is
   ```

3. `heading` and `position` become NaN at the same time. After that, inside `moveToward` (index.mjs:628-642),
   `Math.atan2(dest.y - NaN, dest.x - NaN)` keeps producing NaN every frame — **NaN sustains itself**.
4. The `Number.isFinite` guards in the engine are added only on the input side (`setMargins:198`, `setAvoidRadius:770`,
   `speedMultiplier:736` of `suggestMoveTo`). **`position` / `heading` have no guard at all.**

### The recovery path is unreliable (measured)

```bash
curl -s -X POST http://127.0.0.1:47811/control -d '{"resetPosition":true}'
# → {"applied":["resetPosition"],"ok":true,"rejected":[]}
```

`main.ts:350-351` does listen for `reset-position` and call `engine.resetPosition()`,
but **24 seconds of continuous sampling after that (once every 2 seconds) still showed an illegal position**:

```
t+ 2s  wander  position valid=false  {"x":null,"y":null}
t+12s  idle    position valid=false  {"x":null,"y":null}
t+24s  idle    position valid=false  {"x":null,"y":null}
```

`resetPosition()` (index.mjs:790-800) resets `position / state / idleUntil / target / aiIntent /
dragStuckSinceMs / holdUntil`, **but it does not reset `heading`, and it does not touch the internal smoothing state of the render layer (body-controller / spring)**.
So the engine side is cleared, and the render layer is still NaN.

**About 10 minutes later the cat recovered on its own** (the position returned to the left edge, `x≈32`). But **the trigger of the recovery cannot be determined** —
no interface can query `heading` or the current expression, and there is no event log. A reproducible "disappearance" paired with an
unexplainable "recovered on its own" is itself evidence that the troubleshooting means are insufficient (see item 6).

### Impact and severity

- Any process that can reach `127.0.0.1:47811` can **make the user's cat disappear permanently**, and the API reports success the whole way.
- The easiest way to hit it is an LLM: when it is unsure of the field shape it sends `{}`, `{x:null}`, or an unfilled variable in a template.
- The fallback the docs claim ("reset position") does not work in this scene, and the user will think the app is broken.

### Suggested direction (not implemented)

1. Validate at the Rust `/intent` boundary: `targetPoint.x/y` must be finite numbers, otherwise 400 and explain why.
2. On the `suggestMoveTo` side, change it to "illegal means ignore the whole intent" rather than handing it to clamp.
3. `resetPosition()` should also reset `heading`, and notify the render layer to rebuild its smoothing state.
4. Add an invariant check in the engine: once `position` or `heading` is non-finite, go straight back to `resetPosition()`.

## 2 [medium-high] Several reminders coming due together are silently swallowed

### Code

`apps/lingxi/src-tauri/src/lib.rs:940-965`:

```rust
for reminder in reminders.iter_mut() {
    if !reminder.done && reminder.due <= now {
        reminder.done = true;          // ← all of them marked done
        fired.push(reminder.clone());
    }
}
...
if let Some(reminder) = due.first() { /* only the first one is spoken */ }
```

### Reproduction

```bash
for i in 1 2 3; do
  curl -s -X POST http://127.0.0.1:47811/reminders \
    -H 'Content-Type: application/json' -d "{\"text\":\"吞掉测试-$i\",\"inMinutes\":-1}"
done
sleep 36      # the ticker goes once every 30s
```

`吞掉测试` means "swallow test". Result in `reminders.json`:

```
done=true  吞掉测试-1     ← will be spoken
done=true  吞掉测试-2     ← lost permanently
done=true  吞掉测试-3     ← lost permanently
```

`done` is `true` for all three, but only the first one is spoken. **The user neither saw the other two nor can get them back.**

The intent written in the comment is right ("a cat that recites a backlog at you is a todo list, not a pet").
The implementation should **postpone** the rest (keep `done=false`, and play one more next round), not **discard** them.

A real scene that triggers it easily: the user closes the app for a while, and several reminders are overdue together when they come back.

Control: the path for a single reminder is completely normal — a reminder with `inMinutes:-30` fired on time, and `done` flipped correctly.

## 3 [medium] False success: the interface reports success, and it did not take effect

Once a caller (especially an LLM) gets `ok:true` it will not retry, so the error is **never discovered**.

### 3.1 A misspelled `action` / `expression` is not reported (it reaches the MCP layer)

```bash
curl -s -X POST http://127.0.0.1:47811/control \
  -H 'Content-Type: application/json' \
  -d '{"action":"this-action-does-not-exist","expression":"这个表情也不存在"}'
# → 200 {"applied":["action=... (forwarded)","expression=... (forwarded)"],"ok":true,"rejected":[]}
```

`这个表情也不存在` means "this expression does not exist either".

**The same holds through MCP.** Measured: `lingxi_express({action:"totally-fake-action-id"})` returns:

```
Applied: action=totally-fake-action-id (forwarded), expression=根本不存在的表情 (forwarded)
```

`根本不存在的表情` means "an expression that does not exist at all".

That is, the model will report to the user "I made the cat say hello", and the cat did nothing.

Control: `perform` / `camera` / `skin` / `scale` / `toy` go through Rust validation, and a misspelling is a clear 400:

```bash
curl -s -X POST .../control -d '{"perform":"nope"}'   # → 400 perform: unknown performance "nope"
```

### 3.2 Over-long text in `lingxi_say`: silent truncation + a lie

On the Rust side, `text.trim().chars().take(140)` (lib.rs:913) truncates silently,
but the MCP tool returns `Said: <the full original text>`. Measured: sending 150+ characters, the tool echoed the full text, and the cat showed only the first 140 characters.

### 3.3 `kind` on `/memory` has no enum check

Measured: `{"text":"测试非法kind","kind":"hack"}` → `ok:true`, and **`"hack"` is written as-is into
`memory.json`, which the user will open**. `测试非法kind` means "test an illegal kind". `remember` (lib.rs:1268-1290) falls back to `"moment"` only when `kind.is_empty()`;
any other string is stored as-is. The documented enum is `owner/project/preference/moment`.

MCP's `enum` stops it. Bare HTTP does not → a plaintext file the user can see develops schema drift.

### 3.4 An empty string `action: ""` is treated as success

```bash
curl -s -X POST .../control -d '{"action":""}'    # → 200 {"applied":["action= (forwarded)"],"ok":true}
curl -s -X POST .../control -d '{"say":"   "}'    # → 400 say: empty text
```

The same kind of empty value: one is rejected, one is allowed.

### 3.5 Other silent truncations

`remember`'s `.take(280)` (lib.rs:1269) and `/reminders`' `.take(140)` (lib.rs:1092)
do not say so. Measured: a 200-character reminder is stored as 140 characters, and the return is still `ok:true`.

**Shared suggestion**: truncation must be marked truthfully in the response (for example `applied:["say (truncated to 140)"]`);
empty values and illegal enums should be rejected and explained.

## 4 [medium] Silent failure: the caller thinks it sent something, and the interface says "you sent nothing"

The same class of problem as item 3, in the opposite direction.

`apply_control_command` reads values only with `command.get("field").and_then(|v| v.as_str())`.
If it cannot get one, it skips it silently, and at the end reports `empty command` for all of them:

| Sent | Returned | The truth |
|---|---|---|
| `{"expresssion":"开心"}` | `empty command: expected at least one of ...` | The field name is misspelled. `开心` = happy |
| `{"scale":"big"}` | the same | The type is wrong (`.as_f64()` returns None) |
| `{"visible":"yes"}` | the same | The type is wrong (`.as_bool()` returns None) |
| `{"expression":null}` | the same | The value is null |
| `{"nonsense":1}` | the same | An unknown field |

The caller will think it sent no parameters, and then **retry or give up**, instead of fixing the field name.
Suggested: distinguish three cases: unknown field / wrong type / really nothing was sent.

### `holdMs` has no bounds, and an illegal value falls back silently

| Input | Result |
|---|---|
| `holdMs: -99999` | `as_u64()` fails → **silently falls back to 4000** |
| `holdMs: "abc"` | the same (control: `scale:"big"` reports an error clearly; this does not) |
| `holdMs: 99999999` | **accepted** (about 27 hours) |

`holdMs` on `/intent` also has no upper bound (`until: now + holdMs`, index.mjs:732),
and it can leave the cat stopped at one point for a long time.

**Measured consequence**: after I set `holdMs` to 99999999, **no interface could confirm what expression the cat's face is pinned to now**,
and it also could not confirm whether it had recovered — because `/perception` does not expose the expression (see item 6).

### Reminder parameters are not validated

- `inMinutes: -30` → accepted, and it comes due immediately (then it gets swallowed by item 2)
- Giving both `inMinutes` and `dueAt` → **`dueAt` silently wins** (lib.rs:1095-1098), with no notice.
  The MCP description says "Use this OR dueAt".

## 5 [low-medium] Inconsistent error presentation at the MCP layer + dead code in `tools.mjs`

### Two error styles

| Tool call | What the model actually sees |
|---|---|
| `lingxi_express` (no arguments) | `Give an expression, an action, or both.` ✅ |
| `lingxi_remind` (missing a time) | `Give inMinutes or dueAt.` ✅ |
| `lingxi_look` (no arguments) | `Give a camera, a skin, or both.` ✅ |
| `lingxi_say` (blank text) | `/control returned 400: {"applied":[],"ok":false,"rejected":["say: empty text"]}` ❌ |
| `lingxi_perform` (wrong id) | `/control returned 400: {"applied":[],"ok":false,...}` ❌ |

### Root cause: a piece of code that never runs

In `packages/mcp-server/src/tools.mjs`, `lingxi_say` / `lingxi_play` / `lingxi_look` /
`lingxi_perform` all have:

```js
if (result.rejected?.length) throw new Error(result.rejected.join('; '));
```

But `call()` in `bridge.mjs` **throws first** when `!response.ok`, and `/control` returns 400 as soon as there is any
rejected. **So these branches are unreachable** — the carefully written `rejected.join('; ')`
message has never appeared in a single real error.

The same check in `lingxi_express` is worse: its `action`/`expression` are forwarded, and `rejected` is always empty,
so this `if` gives the impression "it has already been validated", and in fact it is the direct source of the false success in item 3.1.

### The MCP schema is not fully aligned with the real capabilities

- `lingxi_say.text` has no `maxLength`, and the bridge truncates to 140
- `lingxi_remember.text` has no length constraint, and the bridge truncates to 280
- `inMinutes`/`dueAt` on `lingxi_remind` are "one or the other", but in the schema both are optional and there is no
  `anyOf`/`oneOf` constraint, so it can only fall back to throwing at runtime

### One place that is done well (usable as a template)

`toy` on `lingxi_play` uses `enum` to stop an illegal value **at the protocol layer**:

```
Parameter validation failed: /toy: must be equal to one of the allowed values
```

It never reaches the bridge. This is the cleanest validation in the whole project.

## 6 [low] Observability gaps

### 6.1 `/perception` does not expose the current expression or `heading`

The snapshot has `action` (the action currently playing), `toy`, and `petState`, but **not "what the current expression is",
not `heading`, and not "what the current AI intent is"**.

Hit in measurement: after setting `holdMs` to about 27 hours, no interface could confirm what state the cat's face was pinned in;
while investigating the NaN of item 1, there was also no way to know whether, and when, `heading` recovered.

`/perception` is the only observation surface for a third-party driver. Without these fields, "after driving, you do not know the effect" is inevitable.

#### Addendum: `GET /status` has half the answer, and the boundary is worth stating clearly

This item was put too loosely before. Measured (2026-09-19 09:20), `GET /status` returns:

```json
{"activeAgent":"none","behaviorPreset":"lively","camera":"game","catName":"灵犀",
 "mode":"free","scale":0.25,"skin":"moon-oat","visible":true}
```

So the observation surface is actually split like this:

| Field | `/perception` | `/status` | Can the driver prove it took effect |
|---|---|---|---|
| `skin` | ❌ | ✅ | **Yes** |
| `camera` | ❌ | ✅ | **Yes** |
| `scale` | ❌ | ✅ | **Yes** |
| `visible` | ❌ | ✅ | **Yes** |
| `toy` | ✅ | ❌ | Yes |
| `action` (the action currently playing) | ✅ | ❌ | Yes (with a delay; see the skill) |
| **`expression` (the current expression)** | ❌ | ❌ | **No ← the only one that is completely invisible** |
| **`heading` (facing)** | ❌ | ❌ | No |
| **`aiIntent` (the current AI intent)** | ❌ | ❌ | No |

**The conclusion should be narrowed**: the gap is not "you cannot see anything". It is that **expression, heading, and intent are dark on every endpoint**.
Of those, `expression` does the most harm — it is the only control that "can be sent, can be changed, and after sending cannot be verified at all",
which makes the false success of #3.1 **undetectable** for expressions (see clarification two in the field note of the interface-requirement section).

Incidentally: `skin` in `/status` also makes the control for #13 sharper —
**the user can have it + the interface can read it + but an agent cannot write it**. All three sides are present, and only the write entry is blocked by hard-coding.

### 6.2 NaN disguises itself as `null`

When position becomes NaN, JSON serialization produces `{"x":null,"y":null}`.
An external driver that receives `null` **cannot tell "the cat is broken" from "the field is missing"** — a silent failure.
Suggested: either do not send an illegal value (send the last valid position), or explicitly carry a `degraded`/`health` flag.

### 6.3 `/task-event` accepts an empty object and occupies the event buffer

```bash
curl -s -X POST .../task-event -d '{}'   # → 200 {"ok":true}
```

`normalize_claude_hook_event` normalizes it into an event of unknown state. It **does not trigger a reaction**
(the `_ => return` in `react_to_task_event` stops that), but the event still does `sequence += 1`
and is pushed into `ClaudeHooksState.events` (cap 500).
Any process that can reach loopback can **flood junk events and push the real history out of the buffer**.

(The comment explains that 200 means only "received", not "understood", and that is intentional; but there is no branch for "unrecognized, so discard".)

### 6.4 There is no event log that can reconstruct the scene

Item 1 hit this in measurement: the cat disappeared and then recovered on its own, and I **could not answer** "when it disappeared, when it came back,
and why it came back". T7 in `CODE-AUDIT-2026-09-13.md` suggested a ring event log + `GET /debug/events` long ago,
and it still does not exist. This is the item in this round that most affects troubleshooting efficiency.

### 6.5 `/intent` can be written and cannot be read (an asymmetric design)

You can POST an intent, but no interface can read back "what the current intent is, and when it expires".
The engine has `aiIntent` internally, and the outside cannot see it. Investigating "why the cat keeps walking in some direction" is guesswork.

## 2. [Severe · new] The bridge has no auth and is open cross-origin to any web page

**This is the most severe finding of this round, and it had not been recorded before.**

```
$ curl -s -i -X OPTIONS http://127.0.0.1:47811/control -H 'Origin: https://evil.example' \
    -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type'
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: *          ← every response carries this header

$ curl -s http://127.0.0.1:47811/memory -H 'Origin: https://evil.example'
Access-Control-Allow-Origin: *
{"notes":[{"text":"喜欢先把根因量出来再动手改",...}]}    ← the user's private notes are returned

$ curl -s -X POST .../control -H 'Authorization: Bearer totally-bogus' -d '{"expression":"开心"}'
{"applied":["expression=开心"],"ok":true,...}            ← a fake token is ignored completely
```

**Impact**: `Access-Control-Allow-Origin: *` + no auth = **any web page the user visits in a browser**
**can, with a few lines of JS, read the entire memory of their desktop cat, drive the cat, write reminders, register an agent, and flood events.**

```js
// paste into the console of any web page to reproduce
await (await fetch('http://127.0.0.1:47811/memory')).json()          // read private notes
await fetch('http://127.0.0.1:47811/control', { method:'POST',
  headers:{'Content-Type':'application/json'}, body:'{"expression":"惊吓"}' })
```

This is not the weakened claim "a local process can reach it" — the preflight returns 204 and carries `ACAO: *`,
which means the browser **will actually send the request and allow the page to read the response**, without the user clicking anything.

**Supporting evidence**: `integrations/cli/lingxi`, added to the workspace at 15:38, already uses
`Authorization: Bearer $(cat bridge-token)`, which says the author has already decided to add auth — it just **has not entered a build yet**.
After auth is added, the cross-origin path that reads the response breaks on its own (a web page cannot read the token on disk).
But **auth alone is not enough**: `ACAO: *` should be narrowed at the same time, or a request can still at least be **initiated** cross-origin.

| C7 | **A partial apply returns 200 + a non-empty `rejected`** | `{"say":"hi","holdMs":"abc"}` → `200 {applied:["say"], rejected:["holdMs: ..."]}` | A caller that only checks the status code misses the failure. The MCP layer unpacks it; a bare-HTTP caller does not |
| C8 | **Bare-HTTP `reloadAssets` is asynchronous** | Returns `{"ok":true, "note":"The reload is asynchronous. Poll GET /assets/status ..."}`; when a file is bad, `ok` is still `true` | There is a `note`, so it is an intentional design; but a caller that only looks at `ok` will misjudge "the assets loaded successfully". MCP's `lingxi_reload_assets` already waits 600ms internally and avoids this |
| C9 | **A far-away coordinate is accepted, and the target that takes effect is not reported** | `{"targetPoint":{"x":1e9,"y":1e9}}` → 200; the `intent.target` of `{"x":10,"y":20}` becomes `{x:10, y:86.33}` (clamped by the engine into the valid band) | Silent clamping is reasonable in itself, but the response does not tell the caller "the point you requested was changed to here" |
| C10 | **The registry is not persisted, but the copy says "once"** | After a real restart, `GET /agents` → `[]`; while the note on `POST /agents` says "Register yourself ... once, at the start of a session", and `/integration` says "POST /agents once" | An app restart clears the registry, and the agent cannot tell → afterwards it appears as `anonymous` (💻), and the user cannot tell who it is. The wording should say explicitly "once per application lifetime" |
